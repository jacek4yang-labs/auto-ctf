## 4. 2024 决赛 5 道 Pwn —— 原创二进制深度分析（本报告核心增量）

> 题库中唯一没有题解的部分。以下全部结论来自 objdump 反汇编 + WSL 实际运行验证。

### 4.1 总体画像

| 题目 | glibc | PIE | RELRO | Canary | 难度 | 漏洞本质 |
|---|---|---|---|---|---|---|
| springboard | 2.23 | PIE | Full | 无 | ★★ | 格式化字符串（16B/轮，无限轮） |
| ez_exchange | 2.31 | PIE | Full | 无 | ★★☆ | 16 字节栈溢出（恰好 rbp+ret） |
| baby_linklist | 2.31 | **No-PIE** | **Partial** | 未见 | ★★★ | 链表删除语义缺陷（free next 元素） |
| story | 2.31 | PIE | Full | 有 | ★★★★ | UAF（delete 不清指针）+ show 无边界检查 |
| Vegetables | 2.27 | PIE | Full | 无 | ★★★★☆ | 受控长度栈溢出（仅够 rbp）+ seccomp |

决赛共同点：全部 x86-64 堆/栈方向、全套现代保护（除 baby_linklist 特意留 No-PIE/Partial RELRO 作出口）、libc 全部随题给出、**没有签到题**——与初赛形成明显难度断层。

### 4.2 逐题分析

#### Vegetables（卖菜·seccomp ORW，最难）

- **程序逻辑**：菜单 1=Buy（`read(0, rbp-0x20, counter)`，**读入长度 = 卖菜游戏得分 counter**），2=Sell（小游戏结算返回得分），3=exit；`init()` 装载手写 BPF seccomp 过滤器；`magic()` 每轮循环调用一次。
- **漏洞 1（溢出）**：Buy 的栈缓冲只有 0x20 字节，读入长度由游戏得分控制。实测游戏机制：**任何 >9 的输入直接结束卖菜环节**（`jmp` 出循环），正确顺序 `-1, 1×8, 10` → bad=18 + flag → **counter = 42**（已在 WSL 实测）。42 字节 = 缓冲 32 + **saved rbp 全 8 字节** + ret 低 2 字节 → 不足 ROP，但足以**完全控制 rbp**，配合 main 的 `leave; ret` 完成栈迁移。
- **漏洞 2（设计好的出口）**：`magic()` 内 `key` 计数器，key==2 时 `mmap(0x6660000000, 0x1000, RWX|FIXED)` 并 `read(0, 页, 0x100)`——正常流程只调用一次（key=1 打印 "wrong place"），**必须靠溢出把 magic 再调一次**才能拿到 RWX 页。
- **seccomp 解码**（手写 BPF，22 条指令）：黑名单 KILL `open(2)/openat(257)/execve(59)/execveat(322)/creat(85)/fork(57)/vfork(58)/clone(56)/tgkill(234)`，其余放行——**连 open/openat 都禁**，glibc 2.27 又没有 openat2 包装，逼选手用 raw syscall 发 `openat2(437)`。
- **完整利用链**：玩小游戏拿 counter=42 → Buy 溢出控制 rbp → main `leave;ret` 迁移到可控区域 → ROP 调 `magic()`（key→2，拿 RWX 页+读 shellcode）→ 跳 0x6660000000 → shellcode 用 **openat2/read/write** 读 flag（open 被禁的绕法）。
- 实测验证：counter=42 ✓、seccomp 解码 ✓、magic 逻辑 ✓。

#### story（UAF + 无边界 show + mmap 邻接 libc）

- **程序逻辑**：标准堆菜单 add/show/edit/delete。全局配额：**add ≤9、delete ≤6、edit 仅 1 次、show 仅 1 次**；idx 0-15；size 强制 0x80-0x3f0（全部落在 tcache 范围，堵死 fastbin）；add 读 size-1 字节后在 `chunk[n_read]` 写 `'0'`。
- **漏洞 1（UAF）**：delete 只 `free` 不清 `list[idx]` → show/edit 均可作用于已释放块。但 delete 有 6 次上限，**凑不满 7 个同 size 填满 tcache 进 unsorted**，常规 libc 泄露被配额堵死。
- **漏洞 2（show 无边界检查）**：add/edit/delete 都校验 0≤idx≤15，**唯独 show 不查**，`printf("%s", list[idx])` 可用任意 32 位带符号索引越界读 `.bss`。**实测**：`show(-23)` 打到 `__dso_handle`（自指向指针），输出 `\x08 @\x05\xafV` = `0x56af05402008` → **PIE 基址泄露成功**。
- **漏洞 3（free-next 删除 + calloc 别名）**：delete 后槽位仍在，同 size add 会从 tcache 取回同地址 → 两槽别名；add 的数据写入可覆盖 tcache entry 的 key 字段（绕 2.31 双重释放检测）实现 **tcache dup**。
- **完整利用链**：show(-23) 泄 PIE → tcache dup + 投毒把分配落到 `.bss` 的 `size[]` 数组（PIE 已知）→ add 写入超大 size → 再次 add 触发 **mmap 大块，mmap 区域恰好贴在 libc 映射正下方**（topdown 分配器特性）→ 用唯一一次 edit 从 mmap 块向 libc 方向越界写 `__free_hook = system`（偏移用题目自带 libc 2.31 计算）→ free 到预置的 "/bin/sh"（写在 .bss 已知地址）→ shell。全链 add/delete 配额刚好够用。
- 实测验证：PIE 泄露 ✓；UAF/dup/投毒每步均为 2.31 标准原语，链路配额核算无冲突。

#### ez_exchange（栈泄露 + 精确 16 字节溢出）

- **程序逻辑**：`fun1` 先 `printf("this %lx ...", &buf)` **泄露栈地址**，然后 `read(0, rbp-0x50, 0x60)`——缓冲 0x50，读 0x60，**恰好溢出 saved rbp + 返回地址 16 字节**；`fun2` 只回显全局 num。整个 main 跑一次就退出。
- **保护**：PIE + Full RELRO + NX，无 canary；只给栈泄露，PIE/libc 基址未知。
- **利用链（已实测核心原语）**：partial overwrite——返回地址只改低 2 字节回跳 main 形成**无限 read/泄露循环**（每次循环帧下移 0x10，可连续布置数据）。实测 1/16 概率成功（PIE 低 16 位中 4 位 ASLR），24 次尝试内验证成功 ✓。循环建立后结合栈泄露做 ROP/one_gadget 收尾（libc 2.31 随题给出）。
- **定位**：教学级 fmt-无、溢出有——考察"溢出窗口刚好 16 字节怎么建立持续控制流"。

#### baby_linklist（No-PIE + Partial RELRO 的链表堆题）

- **结构还原**（stripped，从 entry/main/三个功能函数反汇编还原）：全局 `ctx` 指针 @0x404060；init 读 0x10 字节名字进 ctx+8；**ctx[+0x18] 既是名字区紧邻字段又是链表头**；元素 chunk = `calloc(1,0x20)`，其 `[+0x18]` 字段**同时充当 next 指针**——链表为 ctx→d1→d2→…，配额 insert ≤4 / reset ≤4。
- **关键反汇编证据**：Reset(idx) 的流程是 `read(0, elem, 0x18)`（直接写进链表元素本体）→ `free(elem[0x18])`（**free 的是下一个元素**）→ `elem[0x18]=0`。
- **设计意图**：`calloc` **绕过 tcache 取块**（glibc 行为）堵死"free 后重新 insert 拿回同块"的经典 UAF 路径；同时 No-PIE + Partial RELRO（.got.plt 可写 @0x404018）+ 二进制导入 `__malloc_hook`（GLOB_DAT 槽 0x403fd0 固定存放 libc 地址）说明预期出口是**无泄露打固定地址 GOT/hook**。init 还把 `__malloc_hook-0x890` 置零（防御性 patch，反 one_gadget 直打）。
- **状态**：功能语义 100% 还原，多轮交互序列扫描未见直接崩溃；精确 fault 点（推测在 free-next 与配额计数的组合）需 gdb 动调确认。评级 ★★★。

#### springboard（16 字节预算的无限格式化字符串）

- **程序逻辑**：整个 main 就是一个循环：`puts(">> ")` → `read(0, bss_buf, 0x10)` → `strncmp(buf,"exit",4)` 命中则 `exit(0)` → 否则 **`printf(buf)`**。libc 2.23。
- **漏洞**：教科书级格式化字符串，但每次输入**只有 16 字节**，且 read 不清零缓冲（残余内容可跨轮拼接）。
- **利用链**：`%9p` 等逐轮泄露栈/libc → 多轮 `%hn` 两字节两字节把 one_gadget（或 FSOP 用 vtable，2.23 无 vtable 检查）写到 printf 自己的返回地址 → 发任意非 "exit" 输入让 printf 返回触发。无限轮次 × 16 字节预算 = 把 fmtstr 写成"编程题"。
- **定位**：决赛最易题，考察 fmtstr 手感与预算管理。

### 4.3 决赛横向结论

1. **与初赛的落差**：初赛 pwn 有签到（如 cancanneed 前 half），决赛 5 题全部需要完整攻击链，Vegetables/story 达到难题水准。
2. **出题套路**：每题都设计了一个"不常规的出口"——Vegetables 的 openat2-only seccomp、story 的 mmap-贴-libc、ez_exchange 的 16 字节 partial overwrite、baby_linklist 的 calloc 绕 tcache、springboard 的 16 字节预算——**配额/预算管理是决赛主旋律**。
3. **glibc 版本梯度**：2.23（springboard：hook/FSOP 时代）→ 2.27（Vegetables：无 openat2 包装逼 raw syscall）→ 2.31（story/ez_exchange/baby_linklist：tcache 时代 + key 检测），考察面完整。
4. **后续工作建议**：搭 patchelf + 对应 glibc 的调试环境，用 gdb 确认 baby_linklist 的 fault 点；Vegetables/story 两条链的端到端 exp 编写与远程验证。

## 7. 跨年份考点演进与备赛建议

1. **Pwn**：2022 栈迁移教学 → 2023 带环境交付（Docker/xinetd）+ glibc 版本敏感 → 2024 初赛异构（MIPS 大端）+ 内核（4.4.72 UAF）→ 2024 决赛配额管理型难题。**内核与 seccomp/openat2 是 2024 的分水岭考点**。
2. **Crypto**：2022 LCG 手工数学 → 2023 Coppersmith/EC 组合 → 2024 正交格/apbq + 非平衡素数。**Sage 依赖逐年加重，但队内已验证纯 Python（python-flint LLL）可替代 Sage 完成 Coppersmith 类题**。
3. **Reverse**：VM 逆向是常青考点（2022 infantvm → 2024 downcity 自研 12-opcode VM → 2024 决赛暗示），WASM 在 2024 出现。
4. **Web**：2022 Node/Java 表达式注入 → 2023 云原生（Spark/K8s）→ 2025 Java 反序列化面（XXL-RPC/Motan）。SSRF+gopher+内网组合稳定复现。
5. **Misc**：取证链越拉越长（2024 内存→SQLite→USB 数位板→VeraCrypt 四级），区块链溯源为 2024 特色（但依赖在线链，赛题复现性差）。
6. **flag 风格**：2022-2023 偏 md5 hex 形态，2024 起统一 `[FLAG已脱敏]`，动态题 flag 随环境变化。
